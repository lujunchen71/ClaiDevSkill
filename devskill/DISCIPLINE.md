# 项目纪律（通用版 · 逐字拷贝 · 禁止改写）

> 本文件由 dev-flow skill 分发，任何项目拷贝后逐字生效。项目特有规则**禁止**写进本文件，写进项目自己的 `BOUNDARY.md`。
> 关键词约定：**必须**=MUST、**禁止**=MUST NOT、**应当**=SHOULD、**避免**=SHOULD NOT、**可**=MAY。

## 1. 文档纪律

1. 开工**必须**先有需求与方案文档：现象、目标、方案与取舍、不做什么、验收口径，五段缺一不可。
2. 需求文档**禁止**写执行项拆分、进度勾选、过程记录。
3. 文档按 `v1..vN` 版本化；定稿一版开一版；AI **必须**只读最新版目录。
4. 版本目录之外**禁止**存在散落文档。

## 2. 计划纪律

1. 定版后**必须**把需求拆成 `plan.md`：PX 执行单元（P0..PN），每单元一句目标 + 逐项 checkbox。
2. 执行项**必须**有可判定的验收口径。
3. **plan.md 存在才开始记 worklog**；plan.md 写完**必须**立即提交。
4. plan.md 只管执行：论证回需求文档、过程回 worklog、评审回 review/。

## 3. 执行纪律

1. 按 plan 顺序执行，**做一个勾一个**；**禁止**做完一批补勾。
2. 未做的项保持 `[ ]` 并注明原因；**禁止**伪勾。
3. 新需求**必须**先走需求文档→评审→进 plan，才允许写码。
4. 追加需求时**应当**顺带标记过时/不合理的前置条目，经用户确认后修订。
5. **板块唯一施工权**：多机/多会话/多模型并行同一 worktree 时，一个板块同一时刻**必须**只有一条施工线。开工前**必须**先插旗：在该板块最新版 `plan.md` 顶部登记一行「施工者 + 分支名 + 开始时间」并提交；收工合并后拔旗（同一提交内删除该行）。发现已有旗**必须**先与用户确认归属（接力或等候），**禁止**并行双写同一板块——双写必然冲突/重复实现，合并和解成本远超一次沟通。（出处：一次真实双写事故——两条施工线并行实现同一 plan，11 文件冲突+合并和解。）

## 4. 日志纪律

1. **第 0 铁律：不 push 等于没做**——收工必须 commit && push（代码 + worklog 条目 + plan.md 勾选）。
2. worklog 按 `<平台>-<机器名>-<写作者>.md` 分文件，**只写自己的文件**；条目倒序，最新在顶。
3. **双写顺序**：先 worklog 写 ✅ 记 hash，再勾 plan.md，最后一并提交——崩溃只少勾不多勾。
4. 条目字段、恢复流程、记录纪律按 `WORKLOG-PROTOCOL.md` 执行（本文件不重复）。
5. 代他人补记**必须**标注「代记+依据」。

## 5. 评审纪律

1. 评审记录**必须**进 `review/` 目录，**禁止**散落（聊天、临时文件、其他目录）。
2. 每条评审**必须**含：谁评审、日期、对象、结论（通过/驳回/待办）、证据。
3. 评审结论回灌**必须**走「整理需求/现象文档 → 拆成 plan 条目 → 执行」，**禁止**从评审直接改码。

## 6. 边界纪律

1. 以下任一命中**必须**当日登记 `BOUNDARY.md`：用户明确允许/禁止的做法；同一问题改 ≥2 次；用户反复纠正的同一偏好。
2. 边界条目**必须**含：能做/不能做、原因、反复修改史、登记人、日期。
3. 任何人/机/模型接手**必须**先读 `BOUNDARY.md` 再行动。

## 7. 提交纪律

1. 一切真值以 git 为准；本地未提交内容视为不存在。
2. 提交**应当**按工作线拆分（一条线一个提交），提交信息说清「做了什么、为什么、验证是什么」。
3. 合并/推送前**必须**先拉新。
4. 冲突处理口径由用户拍板后登记进 `BOUNDARY.md`，之后按登记执行。

## 8. 清理纪律

1. 功能稳定后**可**删除旧版计划（更早版本的 plan）；删除前**必须**用户确认。
2. 需求/设计文档、worklog、`BOUNDARY.md`、review/ **禁止**删除。

## 9. 临界规则

- **禁止**无需求文档开工、无 plan 项写码、做完补勾、伪勾、review 散落、边界不登记、日志只留本地、改写本文件。
- **必须**只读最新版、做一个勾一个、结论回灌走文档、接手先读边界、plan 变更即提交、合并先拉新。
