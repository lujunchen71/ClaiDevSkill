# ClaiDevSkill

一套给人和 AI 共同遵守的开发流程规范：开工先分流、文档先评审、计划可勾选、步步留 changelog。**真值只在 git**——换电脑、换会话、换人、换模型，接手者读三样东西（协议、plan.md 的 checkbox、worklog/）即可无缝续做，不用问"上次做到哪"、不用重新读代码猜进度。

## 它解决什么问题

多人协作的真实样子：文档散落在聊天记录和各个目录里，版本对不上；两个人改同一个功能互相覆盖；AI 在聊天里说"做完了"，换个会话就没人知道做到哪。这个 skill 用一套强制流程把协作拉回秩序：

- **AI 开工前先分流**：自动判断任务类别——新功能 / 修 bug / 无法归类，各自走不同流程。新功能从需求文档开始；修 bug 先溯源到当初的开发板块再动手；答不出归属立即停工问人。**任何情况都禁止跳过文档直接写码**。
- **文档自动归类**：每个功能有自己的板块目录（`docs/<领域>/vN/`），需求、计划、日志、评审、边界各就各位；`REGISTRY.md` 一行登记一个板块，找东西不用翻聊天记录。
- **每一步都留 changelog**：AI 的每次操作按标准格式写 worklog——做了什么、怎么验证（写成可重跑的命令，不是叙述）、代码推到了哪个 commit。**进度只认 plan.md 的 checkbox，事实只认 worklog**，口头的一律不算数。
- **标准格式 = 无缝接手**：所有文档从模板逐字拷贝，禁止现场发挥（格式漂移即流程失效）。不同的人、不同的 AI 处理同一个问题时，读到的是同一种结构、同一套口径，不用重新猜对方的思路。

## 为什么它是"治理幻觉的终极武器"

AI 幻觉的最大漏洞不是说错话，而是**无法被证伪**。这套流程把每件事钉在可核验的锚点上：

1. **不 push 等于没做**：未进 git 的进度视为未发生，"我以为做完了"一律不算数。
2. **信任但核验**：接手时不盲信 worklog 里的"已完成"——用 `git merge-base --is-ancestor` 核验条目所记 commit 真的在分支上，再**重跑**条目"验证"字段里的命令。说做完了？证明它。
3. **先复述再动手**：AI 接手后必须先复述"当前在哪个任务、上次做到哪（已核验哪个 commit）、接下来做什么"，人确认无偏差才许写码——幻觉在造成损失之前被拦截。
4. **无文档不开工**：没有需求文档和 plan 条目就没有施工权，从制度上消灭自由发挥。
5. **双写顺序防对不上账**：先在 worklog 记 ✅（带 commit hash）再勾 plan，崩溃时只少勾不多勾，进度永不虚报。

## 特色功能

- **六阶段全流程**：需求 → 多轮评审(v1..vN) → 定版开工 → 执行+worklog → 阶段评审 → 稳定后清理；评审每定稿一轮升一版，AI 只读最新版，杜绝拿旧文档当依据。
- **五段需求文档**：现象 / 目标 / 方案与取舍 / 不做什么 / 验收口径，缺一不可；"不做什么"专门防执行期范围蔓延。
- **plan.md 唯一执行计划**：checkbox 四态（`[ ]` 未开工 / `[~]` 进行中 / `[x]` 完成 / `[!]` 受阻），与 worklog 状态一一对应，是进度的唯一真源。
- **多机不撞车的 worklog**：按 `<平台>-<机器名>-<写作者>` 分文件，每人/每台机器/每个 AI 只写自己的文件，git pull 永远 fast-forward，从根上消灭日志冲突。
- **板块唯一施工权（插旗机制）**：多会话并行同一 worktree 时，开工前在 plan 顶部插旗（施工者+分支+时间，随提交入库），已有旗的板块禁止双写——两条施工线并行实现同一计划，必然换来冲突与合并和解。
- **接手恢复协议**：git pull → 读边界文件 → 恢复流程（grep 锚定进行中任务 → checkbox↔worklog 对账 → 核验 commit 可达 + 重跑验证命令）→ 先复述再动手。
- **BOUNDARY.md 边界登记**：用户明确允许/禁止的做法、同一问题改了两次以上、被反复纠正的偏好，当日登记；任何人/机/模型接手必须先读它再行动——偏好不再靠口头传承。
- **评审回灌纪律**：review 结论必须先整理成需求/现象文档、再拆成 plan 条目才许执行，禁止从评审直接改码。
- **过渡态必须有死线**：任何降级/双轨/豁免类机制立项时写明关闭条件与最迟评估日，每月扫超期项——防止临时方案悄悄沉淀为永久机制。

## 快速开始

1. 把整个 `devskill/` 目录放在工作区最顶层（仓库根目录，与 `AGENT.md` 并列）。
2. 把 `AGENT.md` 拷到项目根目录（或并入已有的 `AGENTS.md`），替换尖括号占位，删除「接入」一节。
3. 建 `docs/REGISTRY.md`（板块登记表：每行 = 板块路径 + 干什么），之后每个新板块在同一 commit 登记一行。
4. 让 AI 读 `AGENT.md`——从下一个需求开始，它就会按流程走：先写文档，再做计划，你确认计划后它才写码。

## 仓内文件

| 文件 | 作用 |
|---|---|
| `AGENT.md` | 项目入口规则：任务分流、硬约束模板、接手协议 |
| `devskill/SKILL.md` | 流程总纲：六阶段、目录结构约定、流转规则、采用方法 |
| `devskill/DISCIPLINE.md` | 纪律条款九章（逐字拷入项目生效，禁止现场改写） |
| `devskill/WORKLOG-PROTOCOL.md` | 工作日志协议：第 0 铁律、多文件分工、恢复流程、条目模板 |
| `devskill/templates/` | 五类文档模板：需求 / plan / worklog / review / 边界 |

> 我建议每个项目都使用这个方法——尤其是人和 AI 混编、多机并行的项目。写文档的几分钟，买的是整条协作链的可信。
